# Payment status and inventory deduction test

**Assignment:** Own the payment-status/inventory-deduction test and state the expected result for a repeated payment event.

**System under test:** SmartServe POS simulated payment endpoint, `POST /orders/{order_id}/pay`. In this prototype, a repeated payment event means sending another payment request for the **same order ID**. There is no external payment gateway webhook in this MVP.

## Test scenario and expected results

Use an isolated test instance with the seeded Latte recipe: one Latte costs KRW 4,500 and requires 250 ml milk and 18 g coffee beans. Create one order for **two Lattes** (KRW 9,000). Record its order ID, starting milk and bean stock, and daily paid-order count and sales total.

| Step | Expected payment/order result | Expected inventory and sales result |
|---|---|---|
| Order created, before payment | Order is `open`; `inventory_deducted=false`; no completed payment | Stock and daily sales are unchanged |
| First successful simulated payment | HTTP 200; same order is `paid`; `inventory_deducted=true`; one payment record | Milk decreases **500 ml**, beans **36 g**; one movement per ingredient; daily paid orders increase by 1 and sales by **KRW 9,000** |
| Repeat payment for the same order ID | HTTP **409** with “This order has already been processed. Inventory was not deducted again.”; order remains `paid`; original receipt remains available | **No further stock deduction**; still one payment record and two ingredient movements; paid-order count and sales total do not increase again |

**Pass condition:** The second request changes none of the saved order, payment, inventory, or sales results. A 409 response is the current API's expected duplicate response; the cashier can recover and show the original receipt.

## How to check it

1. Run SmartServe in an isolated test instance and record `/inventory` and `/dashboard/sales` before creating the order.
2. Create and pay the two-Latte order. Record the order ID and check `/orders/{id}`, the receipt, inventory, and dashboard against the first-payment row above.
3. Send `POST /orders/{id}/pay` again for that exact ID. Check its HTTP status and message, then read the same order, inventory, and dashboard again.
4. Check the database if available: exactly one `payments` row for the order and two `inventory_movements` rows, one for milk and one for beans. Record before/after values and screenshots or response output.
